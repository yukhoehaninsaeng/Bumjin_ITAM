## 1. 문서의 기준과 확정 사항

이 문서는 기존 Bumjin_ITAM의 README와 주요 Python 백엔드 코드를 검토한 PRD 초안을 Markdown으로 정리한 것이다. 저장소에서 확인한 구현과 향후 제안을 구분한다. 실제 NAS 배포 버전과 운영 데이터는 별도 확인이 필요하다.

### 확정된 개발 방향

- PHP를 개발 언어로 사용하지 않는다.
- 기존 Python 기반 Bumjin_ITAM을 확장한다.
- FreeITSM은 기능 구성, 화면, 업무 흐름을 참고한다. PHP 코드 도입·통합은 범위에서 제외한다.
- ITAM, 티켓 관리, 조직 관리를 하나의 제품에서 제공한다.

### 아직 확정되지 않은 제안

- Synology NAS·Docker 운영 유지
- PostgreSQL 도입 및 Excel에서 DB로 업무 원본 전환
- 기존 HTML/CSS/JavaScript 화면의 단계적 모듈화
- Python 웹 프레임워크, 세션 저장소, 작업 실행 방식
- 역할별 세부 권한, SLA, 운영 성능·복구 목표

## 2. 제품 목표

직원, 조직, IT 자산, 지원 요청을 연결해 사내 IT 운영 업무를 관리한다.

직원은 자신의 자산을 확인하고 지원을 요청한다. IT 담당자는 요청자의 소속·자산·과거 처리 이력을 확인하며 업무를 처리한다. 관리자는 조직별 자산과 지원 업무 현황을 파악한다.

대표 흐름:

> 내 노트북에서 고장 신고 → 자산이 연결된 티켓 생성 → 지원팀 접수 → 담당자 인수 → 수리 또는 교체 → 티켓 처리 결과와 자산 변경 이력 기록

| 해결할 문제 | 제공할 기능 |
| --- | --- |
| 자산 정보와 지원 이력이 분리됨 | 자산과 티켓 양방향 연결 |
| 메신저·구두 요청의 진행 상태가 불명확함 | 요청, 담당자, 상태, 기한 관리 |
| 이동·퇴사 후 자산 회수가 누락됨 | 직원 상태와 미반납 자산 연결 |
| 공용 관리자 계정으로 작업자 구분이 어려움 | 개인 계정과 감사 이력 |
| Excel 동시 편집과 관계 관리가 어려움 | DB 기반 저장과 동시 수정 제어 |

| 영역 | 저장소에서 확인한 현재 상태 | 확장 방향 |
| --- | --- | --- |

| QR | 조회·스캔·라벨·PDF 출력 | 기존 주소 유지, 로그인 후 지원 요청 |
| 조직 | Excel 조직 트리와 LDAP 사용자·부서 연결 | 직원·자산·티켓을 함께 조회 |

FreeITSM에서는 직원용 포털, 팀·담당자별 티켓 큐, 자산 연결, 알림, SLA, 회사별 접근 범위를 참고한다. 전체 ITSM 모듈을 초기 범위로 가져오지는 않는다.

## 4. 사용자와 권한

한 사용자에게 여러 역할을 부여할 수 있다. 역할과 접근 가능한 법인 범위를 함께 관리한다.

| 역할 | 주요 권한 |
| --- | --- |
| 일반 직원 | 내 자산, 티켓 등록, 본인 티켓 조회·답변 |
| IT 지원 담당자 | 허용된 큐의 티켓 처리와 관련 직원·자산 조회 |
| 자산 관리자 | 허용된 법인의 자산 등록·배정·반납·수리·폐기 |
| 조직 관리자 | 허용된 법인의 조직·직원·소속 관리 |
| 시스템 관리자 | 계정·역할·범위, LDAP, 운영 설정 |

- 모든 조회·수정·다운로드 API에서 서버가 권한을 검사한다.
- 일반 직원은 다른 직원의 자산·티켓을 임의로 조회할 수 없다.
- 티켓 처리 권한과 자산 수정 권한은 별도다.
- 조직 관리자에게 티켓 본문 열람 권한을 자동 부여하지 않는다.
- 공용 admin은 초기 설정·복구용으로 제한하고 일상 업무에는 개인 계정을 사용한다.
- 법인 간 이동·연결은 양쪽 범위에 대한 권한과 명시적인 작업을 요구한다.

## 6. IT 자산관리 요구사항

### A-01. 등록·검색

유형은 PC, 노트북, 모니터, 프린터, 네트워크 장비, 기타로 시작한다.

| 구분 | 항목 |
| --- | --- |
| 식별 | 내부 UUID, 관리번호, 시리얼번호 |
| 기본 | 자산명, 유형, 제조사, 모델, 사양 |
| 소유·사용 | 소유 법인, 관리 부서, 사용 직원, 설치 위치 |
| 상태 | 재고, 사용 중, 수리 중, 분실, 폐기 |
| 구매·보증 | 구매일, 금액, 공급업체, 보증 만료일 |
| 연결 | 티켓, 유지보수 계약, 변경 이력 |

기존 UUID·관리번호를 보존한다. 시리얼 중복은 경고하고 관리번호 중복은 차단한다. 기존 법인별 채번 규칙은 이관 전 확인한다. 구매 정보가 없는 기존 자산도 이관할 수 있어야 한다.

### A-02. 배정·반납·상태

- 한 자산은 동시에 한 명의 현재 사용자에게 배정한다.
- 공용 자산은 사용자 없이 관리 부서·위치에 배정할 수 있다.
- 작업자, 시각, 이전·이후 값, 사유를 기록한다.
- 퇴사자 및 폐기 자산에 대한 신규 배정을 차단한다.
- 사용 중인 자산은 반납 또는 명시적인 사용자 변경으로 재배정한다.
- 폐기일·사유를 필수 입력하고 기록을 보존한다.
- 대여·배정 이력을 삭제하지 않는다.

### A-03. 상세·QR

자산 상세에 기본 정보, 배정, 이력, 관련 티켓, 계약을 표시한다. 기존 `/a/{UUID}` 주소가 유지돼야 한다.

비로그인 QR 화면은 최소 식별·상태 정보만 제공하고 개인정보·금액·티켓 내용은 숨긴다. 직원은 로그인 후 권한이 있는 자산에서 요청을 등록한다.

### A-04. Excel 입출력

- 필드 매핑과 저장 전 미리보기 제공
- 오류 행, 중복, 직원 매핑 미확정 건 표시
- 동명이인 자동 확정 금지
- 가져오기 결과·실패 사유 다운로드
- 내보내기에 법인·역할 권한 적용

**수용 기준:** 자산 배정이 자산 상세와 직원의 내 자산에 일치하게 표시되고, 반납 후에도 배정 이력이 남는다.

## 7. 티켓 관리 요구사항

### T-01. 등록

직원 포털·자산 상세·담당자 화면에서 등록한다. 담당자 대리 등록 시 등록자와 요청자를 구분한다.

| 구분 | 항목 |
| --- | --- |
| 필수 | 제목, 설명, 요청자, 유형, 카테고리 |
| 자동 | 번호, 등록자, 생성 시각, 요청 당시 소속 |
| 처리 | 담당 팀, 담당자, 우선순위, 목표 처리일 |
| 선택 | 관련 자산 여러 개, 첨부파일 |
| 종료 | 해결 내용, 해결·종료 시각 |

초기 유형: 장애, 서비스 요청, 문의.

초기 카테고리: PC·주변기기, 계정·권한, 소프트웨어, 네트워크, 기타.

### T-02. 지원팀·담당자

직원의 소속 부서와 지원 업무 큐를 구분한다.

- 담당 팀과 개인 담당자는 별도 필드로 관리한다.
- 팀만 지정된 티켓은 팀 미배정 큐에 표시한다.
- 담당자를 해제해도 팀은 유지한다.
- 담당자는 해당 티켓에 접근할 수 있어야 한다.
- 인수·팀 이동·재배정 이력을 기록한다.

### T-03. 상태

기본 흐름: `접수 → 처리 중 → 해결 → 종료`

추가 상태: 요청자 답변 대기, 외부 업체 대기, 취소.

| 작업 | 규칙 |
| --- | --- |
| 처리 시작 | 담당자 지정 |
| 대기 | 대기 사유 기록 |
| 해결 | 해결 내용 필수 |
| 종료 | 요청자 확인 또는 권한 있는 담당자의 사유 입력 |
| 재개 | 해결·종료 건을 사유와 함께 처리 중으로 전환 |
| 취소 | 사유 기록, 기존 대화·첨부 보존 |

MVP에서는 자동 종료를 사용하지 않는다.

### T-04. 대화·첨부·이력

- 공개 답변과 IT 내부 메모를 구분한다.
- 내부 메모는 직원 화면·알림·API 응답에서 제외한다.
- 작성자·시각과 수정 여부를 표시하고 수정 이력을 보존한다.
- 첨부 다운로드에도 티켓 접근 권한을 적용한다.
- 상태·우선순위·팀·담당자 변경을 시간순으로 표시한다.

### T-05. 우선순위·목록

우선순위는 긴급, 높음, 보통, 낮음이다. 직원은 영향 범위·긴급도를 입력하고 담당자가 최종 우선순위를 조정한다.

기본 큐는 전체, 내 티켓, 팀 티켓, 미배정, 답변 대기, 기한 초과, 해결·종료다. 법인·부서·유형·상태·담당자·기간·자산으로 필터링한다.

### T-06. 자산 연결

한 티켓에 여러 자산을 연결할 수 있다. 자산에서 티켓을 생성하면 해당 자산을 미리 연결한다. 연결 가능한 자산은 권한 범위로 제한한다. 티켓 해결만으로 자산 상태를 자동 변경하지 않는다. 자산 수정은 별도 권한과 명시적인 작업으로 수행한다.

**수용 기준:** 내 노트북에서 등록한 티켓에 요청자·자산이 연결되고, 담당자가 자산의 과거 처리 이력을 확인할 수 있다. 직원에게 내부 메모가 노출되지 않는다.

## 8. 조직·직원 관리 요구사항

### O-01. 조직 구조

기본 구조는 `법인 → 사업부 → 부서 → 팀`이며 모든 단계를 강제하지 않는다. BJC·BJE·BJM의 실제 구분은 확인 후 매핑한다.

- 조직 고유 ID를 사용해 이름 변경 후에도 연결 유지
- 순환 구조 및 동일 상위 조직 내 동일 이름 차단
- 직원·자산이 연결된 조직의 즉시 삭제 차단
- 조직 상세에서 소속 직원·관리 자산 표시

### O-02. 직원

직원 ID, 사번, 이름, 이메일, 소속, 직책, 재직 상태, LDAP 고유 식별자를 관리한다.

직원과 로그인 계정을 분리해 계정이 없는 직원에게도 자산을 배정할 수 있다. 이름·이메일·UID가 변경돼도 이력 연결을 유지한다.

### O-03. 이동·퇴사

- 부서 이동 시 현재 소속과 이동 이력 기록
- 자산 소유 법인·관리 부서는 자동 변경하지 않음
- 티켓에 요청 당시 소속과 현재 소속 구분
- 퇴사자는 로그인·신규 배정 대상에서 제외
- 미반납 자산·담당 중인 티켓을 확인 목록에 표시
- 담당 티켓 재배정과 자산 회수 상태 추적

### O-04. LDAP

| 데이터 | 원본 제안 |
| --- | --- |
| 인증·계정 고유 식별자 | LDAP |
| 이름·이메일 | LDAP 가져오기 |
| 앱 조직·소속 | 앱 DB, 초기 LDAP·Excel 매핑 |
| 자산·티켓·권한 | 앱 DB |

LDAP 가져오기는 변경 미리보기, 추가·변경·누락 결과, 실패 내역을 제공한다. 조회 실패를 퇴사로 간주하지 않는다.

LDAP 부서 쓰기는 별도 관리자 작업으로 유지한다. 앱 조직 편집과 LDAP OU 생성·이동을 분리한다. 쓰기 실패·부분 성공·응답 불명확 상태를 표시하며 결과 확인 없이 자동 재실행하지 않는다.

**수용 기준:** 부서 이동 후에도 자산·티켓 연결이 유지되고, 퇴사 시 회수·재배정 대상이 확인된다.

## 9. 화면 구성

| 화면 | 핵심 기능 |
| --- | --- |
| 직원 홈 | 내 자산, 내 요청, 새 요청, 알림 |
| 운영 대시보드 | 미배정·기한 초과, 자산 현황, 미회수 자산 |
| 자산 목록 | 검색·필터, 등록, Excel, 라벨 |
| 자산 상세 | 정보·배정·이력·티켓·계약 |
| 티켓 수신함 | 큐·필터·목록·대화 |
| 조직도 | 조직 트리·직원·자산 |
| 직원 상세 | 소속·재직·자산·권한 내 티켓 |
| 시스템 설정 | 계정·권한·LDAP·카테고리·감사·작업 결과 |

모바일은 QR 조회, 내 자산, 티켓 등록·답변을 우선 지원한다.

## 10. 데이터·기술 방향

백엔드는 Python으로 개발한다. 프레임워크는 기존 로직 재사용성, 권한, DB 트랜잭션, 운영 편의성을 기준으로 별도 선정한다. PHP 및 FreeITSM PHP 코드 통합은 하지 않는다.

| 항목 | 제안 |
| --- | --- |
| 배포 | NAS·Docker 유지 |
| 백엔드 | 기존 Python 자산·LDAP 로직 검토·재사용 |
| DB | PostgreSQL 우선 검토, NAS 자원 확인 후 확정 |
| 프런트엔드 | 기존 HTML/CSS/JavaScript 단계적 모듈화 |
| 파일 | 영속 볼륨에 첨부 저장, DB에 메타데이터·권한 연결 |
| 작업 | 알림·LDAP 실행 결과와 실패 내역 기록 |
| Excel | 이관·일괄 입력·내보내기 |

핵심 엔터티는 법인, 조직, 직원, 로그인 계정, 역할·범위, 자산, 배정 이력, 티켓, 지원팀, 대화, 첨부, 감사 이력, 외부 동기화 작업이다.

동시 수정은 버전 검사를 통해 덮어쓰기를 방지한다. 내부 DB 변경은 트랜잭션으로 처리하고, LDAP 등 외부 변경은 별도 결과를 기록한다.

## 11. 데이터 이관

1. 운영 XLSX·설정·감사 기록을 백업한다.
2. 자산·직원·조직·SW·계약·이력 매핑을 정의한다.
3. 시험 이관으로 중복·누락·동명이인·미매핑을 확인한다.
4. 법인·유형별 수량, UUID, 배정, 이력을 대조한다.
5. 기존 QR이 동일 자산을 여는지 검증한다.
6. 기존 앱 쓰기를 중지하고 최종 이관한다.
7. 검증 후 DB를 업무 원본으로 사용한다.

상시 Excel·DB 이중 쓰기를 사용하지 않는다. 전환 후 신규 업무 데이터가 발생한 경우 롤백에는 신규 데이터 추출·반영 절차를 포함한다.

## 12. 품질·운영 요구사항

다음 수치는 초기 제안값으로 실제 사용자·NAS 사양에 맞춰 확정한다.

| 항목 | 요구사항 |
| --- | --- |
| 성능 | 자산 1만 건·티켓 5만 건·동시 사용자 30명에서 일반 목록·검색 p95 2초 이내 |
| 충돌 | 동시 수정 덮어쓰기 차단 및 비교·재시도 안내 |
| 보안 | HTTPS, 서버 권한 검사, CSRF·입력 검증, 로그인 시도 제한 |
| 첨부 | 초기 파일당 20MB, 허용 형식 제한, 실행 차단 |
| 감사 | 작업자·대상·시각·변경 전후·결과 |
| 백업 | DB·첨부·설정 일일 백업 및 별도 위치 보관 |
| 복구 | 초기 RPO 24시간, RTO 4시간 |
| 시간 | UTC 저장, 기본 한국 시간 표시 |
| 접근성 | 상태의 색상·텍스트 병기와 키보드 조작 |

SLA는 영업시간·휴일·대기 상태별 시간 정지 규칙을 확정한 뒤 후속 도입한다. MVP는 목표 처리일·기한 초과 표시를 제공한다.

## 13. 성공 지표

출시 후 첫 4주 기준치를 측정하고 목표를 조정한다.

| 지표 | 초기 목표 제안 |

## 14. MVP 출시 조건

- [ ] 직원이 내 자산에서 티켓을 등록하고 답변을 확인한다.
- [ ] 담당자가 팀 큐에서 티켓을 인수·재배정·해결한다.
- [ ] 공개 답변·내부 메모의 접근 권한이 구분된다.
- [ ] 배정·반납·부서 이동·퇴사 처리가 연결된다.
- [ ] 타 직원·허용되지 않은 법인 데이터 접근이 차단된다.
- [ ] 기존 UUID·QR과 필수 자산 데이터가 유지된다.
- [ ] 기존 SW·유지보수 데이터의 이관 결과가 검증된다.
- [ ] 동시 수정 충돌과 LDAP 부분 실패가 표시된다.
- [ ] DB·첨부·설정을 포함한 복구 시험을 통과한다.
